# 流程工程化改造 — 设计共识

> 状态：**设计已定稿**（待编码实现）
> 日期：2026-06-05

## 背景与目标

把 yudao / Flowable 的流程数据**工程化 + 多环境化**：让流程定义像代码一样可版本、可评审、可回滚，并能忠实地反映 dev / test / uat / prod 各环境的真实状态。

现有设计的问题：
- 只有一份 `flows/`，一套文件推到所有环境，环境之间互相污染、且数据并不真正对得上各环境。
- 没有版本概念，看不到流程在某环境里的历史演进。
- 目录分类是手工拍的、随意。
- 只管了流程（BPMN + 元数据），没管**拖拉拽设计的动态表单**数据。

## 已确定的决策

### 1. 按环境分目录（顶层）

根目录直接拆成四个环境目录，各自是该环境真实状态的镜像，互不污染：

```
dev/  test/  uat/  prod/
```

### 2. 版本：全量历史 + 当前可编辑态并存

- **全量历史**：拉取每个流程在该环境**所有已部署的流程定义版本**（v1、v2、v3…），每个版本是**冻结的只读快照**。
- **当前可编辑态**：另存一份设计器里那个**可编辑的 model**（`now/`），它可能**领先于**最新已部署版本（改了但还没发布）。`now` ≠ 最新的 `vN`，两者必须并存、不合并。

### 3. 每个版本/状态 = 一个自包含快照文件夹

`now/` 与 `vN/` **同级平铺**（不再套 `versions/` 中间层）。每个文件夹形状一致、自包含：

```
<flowKey> - <流程名>/
├── now/                        # 当前可编辑态，可 import 回推重新发布
│   ├── <flowKey>.bpmn
│   ├── model.json              # 元数据（含 category 属性）
│   └── form.json               # 绑定的动态表单（无动态表单则省略）
├── v1/                         # 已部署冻结版本（只读）
│   ├── <flowKey>.bpmn
│   ├── model.json
│   └── form.json
├── v2/
└── v3/
```

**读写规则**：只有 `now/` 可写（可 import 回推），`vN/` 一律只读历史。脚本据此判定。

选这种「同级平铺」而非「当前态散根目录 + 历史塞 versions/」的原因（均为操作层面）：
- 流程目录变成「纯一组同形状的状态文件夹」，结构统一。
- 快照写盘只有一份代码（不分当前态 / 历史两套）。
- `diff now/ v3/` 对称干净。
- 读写权限用一条命名规则（`now` 可写、`vN` 只读）即可管住。

### 4. 表单：只管动态表单，内联在每个快照里

- **只纳管动态表单**（`formType=10` / NORMAL，拖拉拽设计、有真正 JSON 结构的那种），作为 `form.json` **内联**进每个快照（`now/form.json`、`vN/form.json`）。
- **自定义表单不管**（`formType=20` / CUSTOM）：它只是 Vue 路由路径（`formCustomCreatePath` / `formCustomViewPath`），跟着 `model.json` 走，不生成 `form.json`。
- 历史版本的表单是**真冻结**的：`bpm_process_definition_info` 表把表单的 `formConf` / `formFields` 在部署时冗余快照了一份，所以每个 `vN/form.json` 是「当时那一版」的精确内容，不是引用。

### 5. 分类：降级为属性，不占目录层

- 事实：分类是**创建/设计流程时的必填 model 属性**，存在 model 上、发布时拷进每个版本。
- 因此**不在仓库里增加分类目录层**，分类只作为 `model.json` 里的一个字段。
- 物理目录**扁平**：环境目录下直接平铺各流程文件夹。
- 「好找」交给脚本：export/import 列流程清单时**按分类分组展示**（读 model.json 的 category 字段）。即「物理扁平 + 逻辑（脚本）分组」。
- 发布脚本里允许用户**选择/切换分类**，默认沿用上一版的分类。

理由：单一事实来源（只在 model.json 一处）、改分类不用在 git 里搬文件夹、跟历史版本天然不打架、契合「自包含快照」原则。

### 6. 脚本行为

- **export（导出/拉取，从服务器到本地）**：交互模式 = **选环境 → 选流程**，一次针对一个环境。
  - `now/`（当前可编辑态）每次都重拉覆盖。
  - 历史版本 `vN/` **增量**：本地已有的版本跳过，只拉新增版本（历史版本冻结不变）。
- **import（回推，本地到服务器）**：交互模式 = **选环境 → 选流程**，只推 `now/`。
  - 只更新模型草稿（不存在则创建），**不执行发布部署**——发布由用户自行去 BPM 后台操作。
- **字段范围**：model.json 保留全部真实配置（含 `managerUserIds`/`startUserIds`/`startDeptIds`/`managerRoleIds` 等人员部门角色 ID，因四环境这些数据同步、ID 一致）；剥掉 `id`/`modelId`/`categoryName`/`formName`/`deploymentTime`/`suspensionState` 等服务端派生与运行时字段；`bpmnXml`、表单分别拆成 `{key}.bpmn` 与 `form.json`。identity 用 `key` 反查 modelId。
- **凭据**：暂保持硬编码在 `bpm_common.py`（私有仓库，暂不处理）。
- **老 `flows/` 目录**：改造时**直接删除**，新结构全靠 export 从各环境重新生成。

## 已验证的 BPM API 机制（实测 + 源码确认）

源码位置：`yudao-cloud/yudao-module-bpm`。formType 枚举：**10 = 动态表单(NORMAL)，20 = 自定义表单(CUSTOM)**。

**拉「当前可编辑态」(now/)：**
- `GET /admin-api/bpm/model/list` → 所有 model（当前可编辑态，含 key/name/category/formType/formId 等）。
- `GET /admin-api/bpm/model/get?id={modelId}` → 含 `bpmnXml` + 元数据（model id 是 UUID）。
- 动态表单：`GET /admin-api/bpm/form/get?id={formId}` → `{conf, fields, name, remark, status}`，落成 `now/form.json`。

**拉「全量历史版本」(vN/)：**
- `GET /admin-api/bpm/process-definition/page?key={key}&pageNo=1&pageSize=100` → 该 key 的**所有版本**（实测 pdp-review_udit2 有 17 版）。⚠️ 列表项**不含** bpmnXml。
- `GET /admin-api/bpm/process-definition/get?id={版本id}` → 单版本完整内容：`bpmnXml` + 元数据 + **冻结的** `formConf`/`formFields`。版本 id 形如 `key:version:uuid`。
- ⚠️ **坑**：老版本若 Flowable 部署已被清理，`get?id` 可能返回 `null`（实测部分测试流程如此）。脚本需容错跳过。
- ❌ `process-definition/list?suspensionState=1` **不可用于取版本**——它只返回激活且当前用户有权发起的流程，是给前端发起下拉用的。

**写回（import，仅针对 now/）：**
- 只做 `PUT /admin-api/bpm/model/update`（`BpmModelSaveReqVO`，带 `bpmnXml`）更新模型草稿；流程不存在则先 `POST /admin-api/bpm/model/create`。
- identity 用 `key`：import 时拿 `key` 去 `model/list` 反查该环境的 `modelId` 再 update。
- ❗**脚本不执行发布部署**（不调 `model/deploy`）。发布与否由用户自行去 BPM 后台操作。这样避免脚本误改生产、也把「何时生效」的决定权留给人。
- `update-bpmn` 已 `@Deprecated`，不用。
- 分类：`GET /admin-api/bpm/category/simple-list` 取 code→name。

**工程化闭环：** 本地改 `now/` → import 更新模型草稿 → 用户去系统点「发布」生成 vN+1 → 下次 export 增量拉到该新版本。

## 待定（暂缓）

- **import 是否推送表单内容**：`model/update` 只接受 `formId`（绑定），不接受表单内容；表单内容走 `form/update`。两种走法待定——A) import 只推 model、`form.json` 仅归档（表单改动去设计器）；B) import 顺带 `form/update` 推表单内容（有跨环境推错风险）。**暂缓，先不管 form。**
